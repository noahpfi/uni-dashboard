Motivation
• Bisher Abfrage von Daten über formale Abfragesprachen (Relationale Algebra)
• SQL basiert auf der relationalen Algebra
• SQL = Structured Query Language
• Vereinfachte Syntax
• Deklarative Sprache („Welche Daten suche ich?“), Definition über Festlegen der
Bedingungen, die von Ergebnistupeln erfüllt werden sollen
• SQL ist nicht nur eine Abfragesprache:
– Abfragesprache (Data Retrieval Language, DRL)
– Erstellung von Relationen, Indexe (Data Definition Language, DDL)
– Veränderung der Inhalte (Data Manipulation Language, DML)
– Transaktionskontrolle und Zugriffskontrolle (Data Control Language, DCL)

Erzeugen einer Tabelle: CREATE TABLE
Erzeugen einer Relation (Minimalform)
CREATE TABLE student
(student_id INTEGER,
name VARCHAR(30))
Erklärung:
• Es wird eine Relation student angelegt und dem Default-Schema zugeordnet.
• Die Tabelle hat zwei Attribute student_id und name.
• student_id hat den Attributtyp INTEGER.
• Name hat den Attributtyp VARCHAR, variable Länge, max. 30 Zeichen.
• Für beide Attribute sind Nullwerte zugelassen (dies ist Default).
• Wir hätten diese Integritätsbedingung auch explizit setzen können mittels
student_id INTEGER NULL,
name VARCHAR(30) NULL

16
Primärschlüssel
Festlegung des Primärschlüssels
1. Das DBS gewährleistet bei Einfüge- und Änderungsoperationen, dass der Wert dieses Attributes bzw.
dieser Attributkombination innerhalb dieser Tabelle stets eindeutig ist.
Die Änderungsoperation wird ansonsten zurückgewiesen.
2. Je Relation kann max. ein Primärschlüssel definiert werden.
3. Je nach DBS müssen die Attribute des Primärschlüssel explizit NOT NULL gesetzt werden.
CREATE TABLE student
(student_id INTEGER,
name VARCHAR(30),
PRIMARY KEY(student_id))
alternativ:
CREATE TABLE student
(student_id INTEGER PRIMARY KEY,
name VARCHAR(30))
Anmerkung: Ist der Primärschlüssel zusammengesetzt, kommt nur die erste Form in Frage.

Kaskadierendes Löschen (cascading delete)
• Problem: was passiert mit Referenzen nach dem Löschen von Tupeln?
• Beispiel: beim Löschen eines Tupels aus student oder lecture sollen auch alle zughörigen Tupel in
der attends-Tabelle mitgelöscht werden.
• Konsistenz der Fremdschlüssel-Beziehungen kann nicht mehr gewährleistet werden.
• Lösung: Referentieller Integritätsbedingungen (referential integrity constraints) (mit oder ohne
kaskadierendem Löschen).
• Kaskadierendes Löschen kann auch über mehrere Stufen (Tabellen) erfolgen.
CREATE TABLE requires(
predecessor INTEGER,
successor INTEGER,
PRIMARY KEY (predecessor, successor),
FOREIGN KEY (predecessor) REFERENCES lecture(lecture_id) ON DELETE CASCADE,
FOREIGN KEY (successor) REFERENCES lecture(lecture_id) ON DELETE CASCADE);

UNIQUE-Klausel
• Stellt sicher, dass das angegebene Attribut bzw. die Attributkombination nur eindeutige Werte enthält.
• Die „UNIQUE-Attribute“ können ebenfalls in REFERENCES-Klauseln referenziert werden 
Referenzierung erfordert eindeutige Referenz für Auflösung
• UNIQUE-Klausel kann im Gegensatz zum Primärschlüssel in einer Relation mehrfach auftreten.
CREATE TABLE professor
(employee_id INTEGER PRIMARY KEY,
name VARCHAR(30) NOT NULL,
type CHAR(2),
room INTEGER UNIQUE);
alternativ:
CREATE TABLE professor
(employee_id INTEGER PRIMARY KEY,
name VARCHAR(30) NOT NULL,
type CHAR(2),
room INTEGER,
UNIQUE(room));
Achtung:
• Jede Relation sollte einen (als solchen ausgewiesenen) Primärschlüssel haben.
• Unique sollte kein Ersatz dafür sein.
• UNIQUE sollte primär zur Erzwingung von Eindeutigkeitsvorgaben bei weiteren Attributen verwendet
werden.

(Un)benannte Integritätsbedingungen
• Alle bisher dargestellten Integritätsbedingungen (integrity constraints) waren unbenannt.
• Gezieltes Löschen bzw. (temporäres) Außerkraftsetzen solcher Integritätsbedingungen in ohne
Identifier nicht möglich.
• Abhilfe: Deklaration als benannte Constraints:
CREATE TABLE requires(
predecessor INTEGER,
successor INTEGER,
CONSTRAINT pk PRIMARY KEY (predecessor, successor),
CONSTRAINT fk_pred_lecture FOREIGN KEY (predecessor)
REFERENCES lecture(lecture_id) ON DELETE CASCADE,
CONSTRAINT fk_succ_lecture FOREIGN KEY (successor)
REFERENCES lecture(lecture_id) ON DELETE CASCADE);
Wichtig: „Sprechende
Namen“ für Constraints
wählen!

• Wechselseitige Referenzierung:
Lösungsmöglichkeiten
1. Mittels der ALTER TABLE-Anweisung (siehe später).
2. Durch gezieltes Ein-/Ausschalten innerhalb einer Transaktion  Deferred Constraint Checking
checkt Constraints erst am Ende der Transaktion.
SET CONSTRAINTS {ALL, constraint-names(n)}
DEFERRED
SQL-Anweisung 1
SQL-Anweisung 2
...
SQL-Anweisung n

24
Weitere Constraints: Check-Klauseln
CREATE TABLE professor
(employee_id INTEGER PRIMARY KEY,
name VARCHAR(30) NOT NULL,
type CHAR(2) CHECK (type IN ('C2', 'C3', 'C4')),
room INTEGER UNIQUE);
Anmerkungen
• Die CHECK-Bedingung kann im Prinzip eine beliebige Expression sein (<, >, IN, EXISTS, etc.).
• Es werden später nur DML-Operationen ausgeführt, für welche die CHECK-Klausel für die betroffenen
Tupel zu TRUE evaluiert wird.
• Die Deklaration einer CHECK-Klausel ist jeweils an eine Tabellen-Deklaration ( CREATE TABLE)
gebunden.
• Seit dem SQL92-Standard gibt es auch „freistehende“ CHECK-Klauseln ( ASSERTIONS), werden
aber kaum verwendet, abgelöst durch nächst mächtigeres Konzept: Trigger.

28
Schemata
• Schemata dienen zur Kategorisierung der Relationen einer (Gesamt-)Datenbank, z.B.
– alle Relationen zum Universität-Beispiel  Schema: University
– alle Relationen zum Stücklisten-Beispiel  Schema: TeileDB
– alle Relationen zum Personal-Beispiel  Schema: PersDB
• Jede Relation gehört zu einem SCHEMA . Relationsnamen innerhalb eines Schemas
müssen eindeutig sein.
• CREATE TABLE [schema.]tabname bewirkt Eintrag der Relation in den Datenbank-
Katalog.
• Der Datenbank-Katalog ist selbst wieder als Sammlung von Relationen realisiert.
• Nicht von allen DBMS unterstützt (z.B. MySQL).

Autorisierung Wirkungsweise/Erläuterungen
• Jeder Benutzer hat die volle Verfügungsgewalt (Lesen, Ändern,
Löschen) über die von ihm/ihr erzeugten („privaten“) Relationen.
• Andere Benutzer haben per Default keinerlei Zugriffsrechte auf „private“
Relationen anderer Benutzer.
• Ein Benutzer kann Zugriffsrechte auf seine „privaten“ Relationen an
andere Benutzer (gezielt oder an alle) vergeben.
• Die Art des Zugriffsrechts kann beschränkt werden (z.B. auf lesenden
Zugriff)
• Beschränkung des Lesezugriffs auf ausgewählte Attribute mittels VIEW-
Mechanismus.
• Beschränkung des Änderungsrechts (UPDATE) auf ausgewählte
Attribute durch explizite Angabe der Attribute in der UPDATE-Klausel.
• Erteilung der Erlaubnis zur Weitergabe („Vererbung“) von
Zugriffsrechten (WITH GRANT OPTION).

Einfügen von Tupeln
Syntaktische Struktur
INSERT INTO Relationsname [ (Attribut1, Attribut2, ...) ]
VALUES (wert , ..., wert ) [, (wert , ..., wert ) ... ]
11 1n 21 2n
Query
Beispiel
I1 „Füge einen neuen Studierenden (Matrikelnummer 25403) ein, dessen Name „Jonas“ ist und aktuell

alternativ

Nullwerte erlaubt sind.
• Die Einfügewerte können als Konstante mittels VALUES-Klausel oder über eine Query angegeben
werden (INSERT INTO .. SELECT .. FROM …).

FROM Relationsname
[WHERE Bedingung ]
Anmerkung: Löscht alle Tupel, für die die WHERE-Bedingung (falls angegeben) erfüllt ist, aus der

DELETE
FROM attends
WHERE student_id NOT IN
(SELECT student_id
FROM student)

Anmerkung zur Verwendung von GROUP BY
In der SELECT-Klausel dürfen nur Attribute stehen, die auch in der GROUP-BY-Klausel
auftreten:
SELECT p.employee_id
FROM professor AS p
JOIN lecture AS l ON (p.employee_id = l.lectured_by)
GROUP BY p.employee_id
HAVING COUNT(p.employee_id) >= 2
Der folgende Ausdruck ist nicht korrekt:
SELECT p.employee_id, p.name
FROM professor AS p
JOIN lecture AS l ON (p.employee_id = l.lectured_by)
GROUP BY p.employee_id
HAVING COUNT(p.employee_id) >= 2
Warum?
• Je Gruppe wird nur ein Resultat-Tupel ausgegeben.
• Jede Spalte, die ausgegeben werden soll, darf daher innerhalb einer Gruppe keine
unterschiedlichen Werte aufweisen.
• SQL erzwingt dies dadurch, dass nur solche Attribute in der SELECT-Zeile auftreten
dürfen, die auch in der GROUP-BY-Klausel auftreten.
• Teils in DBMS gelockert (vgl. z.B. MySQL Strict Mode)

Bedeutung und Behandlung von Nullwerten
Nullwerte haben die Bedeutung „Wert nicht bekannt“ oder „Wert prinzipiell nicht vorhanden“
und sind verschieden von dem numerischen Wert 0 und einer Zeichenkette der Länge 0.
Behandlung von Nullwerten
• Selektion bzgl. Nullwerten: ... WHERE Attr IS [ NOT ] NULL
• Sortieren nach nullwertigem Attribut:
Tupel mit Nullwerten in dem betreffenden Attribut stehen am Anfang oder Am Ende der
Ergebnis-Tabelle, egal ob ASC oder DESC angegeben wurde. In einigen Systemen
steuerbar über NULLS {FIRST | LAST}
• In arithmetischen Ausdrücken:
Wenn einer oder beide Operanden nullwertig sind, ist das Ergebnis NULL.
124
Bedeutung und Behandlung von Nullwerten
• Logische Ausdrücke werden nach den folgenden Tabellen berechnet:
not and true unknown false or true unknown false
true false true true unknown false true true true true
unknown unknown unknown unknown unknown false unknown true unknown unknown
false true false false false false false true unknown false
• Bei Gruppierung (GROUP BY) nach nullwertigem Attribut: Nullwert wird wie ein normaler
Wert behandelt, bildet ggf. eine eigene Gruppe.
• Bei Anwendung von Aggregatfunktionen (AVG, SUM, COUNT, ...): Nullwerte werden bei
der Auswertung ignoriert.

Definition von Sichten (Views)
Sichtenkonzept von relationalen Datenbanken ist ein wichtiges Mittel zur Erhöhung der
Datenunabhängigkeit von Anwendungsprogrammen.
Allgemeines
• Sicht/View = „virtuelle“ (abgeleitete) Relation
Zweck
• „Ausblenden“ von Attributen (Datenschutz-, Vertraulichkeitsaspekte)
• (Versteckte) Vorformulierung von (häufigen, komplizierten) Anfragen
• Prinzipiell sehr mächtiges Konzept, heute allerdings (oft) noch starke
Implementierungsrestriktionen hinsichtlich Änderungsoperationen.
Syntaktische Struktur
CREATE VIEW Viewname [ ( Attrib1, Attrib2, ... ) ]
AS Query
[ WITH CHECK OPTION ]
130
DROP VIEW Viewname
Sichten Anmerkungen
• Query kann beliebig komplex sein.
• UPDATE und DELETE auch über Views möglich, wenn
– Die View-Definition keine Joins enthält,
d.h. der View nur eine (Basis-)Relation zugrunde liegt oder sich die
Operation eindeutig zuordnen lässt.
– die View-Definition keine DISTINCT-Klausel enthält
– die View-Definition keine GROUP-Functions (AVG, SUM, ...) enthält
(normale „Expressions“ sind erlaubt!).
• INSERT über Views möglich, wenn UPDATE-/DELETE-Restriktionen erfüllt
sind, keine „Expressions“ vorkommen, und keine NOT NULL Attribute
wegprojeziert wurden.
• Mit CHECK OPTION Implementierung von Integritätsbedingungen möglich.
Es können dann nur solche Tupel mit Insert eingefügt oder per Update geändert
werden, die (auch nach der Änderung noch) im „Sichtfenster“ liegen.

Trigger
• Datenbank-“Prozeduren“ (auch ECA-Regeln (Event-Condition-Action) genannt),
die ereignisorientiert aktiviert werden.
139
Trigger Erläuterungen
• Die Angabe „INSERT“ bzw. „DELETE“ bzw. „UPDATE“ entscheidet darüber, welches
Ereignis den Trigger „aufwecken“ soll. In manchen Systemen ist pro Tabelle nur je ein
Trigger für INSERT bzw. für DELETE etc. erlaubt.
• Die Angabe „BEFORE“ bzw. „AFTER“ entscheidet darüber, ob der Trigger vor oder nach
Ausführung der entsprechenden SQL-Anweisung aktiviert wird.
• Bei Angabe von FOR EACH STATEMENT wird der Trigger bei einem SQL-Statement,
das einen mengenwertigen Update / Insert / Delete auslöst, nur einmal aktiviert
(statement-orientierter Trigger)
• Bei Angabe von EACH ROW wird der Trigger für jedes betroffene Tupel aktiviert (tupel-
orientierter Trigger).
• Die (optionale) WHEN(condition)-Klausel erlaubt zu überprüfen, ob die Trigger-
Statements wirklich ausgeführt werden sollen.

Trigger Beispiel: Bestandsschutz (MySQL)
T1 „Erstelle einen Trigger, der sicherstellt, dass Professoren in ihrer Stellung nie abgewertet
werden können (C2 < C3 < C4).“
DELIMITER $$
CREATE TRIGGER professorPromotion
BEFORE UPDATE ON professor
FOR EACH ROW
BEGIN
IF OLD.type IS NOT NULL
THEN
IF OLD.type = 'C3' AND NEW.type = 'C2'
THEN SET NEW.type = 'C3';
END IF;
IF OLD.type = 'C4'
THEN SET NEW.type = 'C4';
END IF;
IF NEW.type IS NULL
THEN SET NEW.type = OLD.type;
END IF;
END IF;
END$$
DELIMITER ;

Trigger Beispiel: Kaskadierendes Löschen
T2 „Kaskadierendes Löschen für TeileBest, TeileBestPos und Liefert bei Löschen eines
Tupels in Lieferant:“
CREATE TRIGGER LiefDelCasc
AFTER DELETE ON Lieferant
REFERENCING OLD AS DelTupel
FOR EACH ROW
BEGIN
DELETE { Löschen der Tupel in Liefert }
FROM Liefert
WHERE Liefert.LiefNr = DelTupel.LiefNr;
DELETE { Löschen der „abhängigen“ Tupel in TeileBestPos }
FROM TeileBestPos
WHERE BestNr IN
(SELECT BestNr
FROM TeileBest
WHERE TeileBest.LiefNr = DelTupel.LiefNr );
DELETE { Löschen der Tupel in TeileBest }
FROM TeileBest
WHERE TeileBest.LiefNr = DelTupel.LiefNr;
END

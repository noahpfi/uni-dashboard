Kurzer Ausflug: Unit Tests / Entwicklertests
• Mit Unit Tests(dt. Modultests) werden einzelne Komponenten getestet
– Heutzutage sind diese Tests weitgehend automatisierbar (z.B. mit JUnit,
JEST, …)
– Modultests sollten isoliert von anderen Modulen laufen
• => Nachgeordnete Module werden „simuliert“ (engl. MockObjects)
• Test Suite: Zusammenfassung verwandter Tests
• Integrationstests: Sammlung von Tests zur Prüfung des gesamten
Systems in einer produktionsnahen Umgebung
• Regressionstests: Sammlung von Tests zur Prüfung der bereits
umgesetzten Funktionalität
– Regressionstests stellen sicher, dass Modifikationen / Erweiterungen von
Modulen/Systemen keine Fehler in vorhandenen Funktionen nach sich
ziehen. => Idealerweise als automatisierte Tests
• Entwicklertests: Tests die der Softwareentwickler für seinen eigenen
Code durchführt.
• Testüberdeckung: Metrik(en) für die Messung der Testqualität

Zielsetzung des Testdrehbuchs (für System-/Abnahmetests)
• Definition des Testablaufs
– Testeingangskriterien
• Wann kann der Test gestartet werden (z.B. nach erfolgreichem Systemtest,
Bereitstellung der Testumgebung, …)

Wie finde ich geeignete System-/Abnahmetests?
• Aus dem Pflichtenheft
– Standardfunktionalität:
• Jeder Use Case liefert einen oder mehrere Tests
Ggf. auch weitere Abläufe und Interaktionen mit dem Arduino/Raspberry
(z.B. Synchronisation)
– Test von Fehlersituationen
• Falsche Eingaben: z.B. Text statt numerischer Eingabe
• Grenzwerte, bzw. Werte außerhalb der Spezifikation
 Achtung: Flächendeckende Fehlertests (hohe Coverage) sindsehr
aufwendig!
– Ggf. auch
• Manueller Code Review / Automatisierte Prüfungen
• Performanztests(aus Pflichtenheft abgeleitet)
• Penetrationstests (z.B. XSS, SQL-Injection)

Beschreibung eines funktionalen Tests
• Testbeschreibung
– Testname/ Kürzel
– Referenz auf Anforderung (z.B. Name des Use Cases)
– Eingaben/Aktionen/Testschritte für das Ausführen des Tests
– Erwartetes Ergebnis (ggf. pro Schritt, oder am Ende)
– Ggf. Beschreibung der Testdaten
• Testdokumentation
– Testergebnis: OK, Nicht OK, oder Bewertung (von kosmetischbis
fatal)
– Ggf. Referenz auf Issueim Issue-Tracker
– Ggf. weitere Informationen zur Reproduzierbarkeit des Tests

[aus Projekt SoSe 2021]
UC Auth1 -Login Nutzer
Auslösender Akteur Beliebiger Nutzer
Vorbedingung Mitarbeiter ist nicht eingeloggt.
Basisablauf 1. Der Nutzer gibt einen beliebigen Link für die Anwendung TimeFlipein (oder folgt
einem Link zur TimeFlipPlattform).
2. Die Login-Maske erscheint.
3. Der Nutzer gibt seine UserIdund sein Nutzerpasswort ein und klickt Login.
Nachbedingung Der Nutzer ist angemeldet.
Der Nutzer sieht die angewählte Seite (sofern er die Berechtigung hat)
Alternative Abläufe, Ausnahmen Wurden bei Schritt 3 eine falsche UserIdoder ein falsches Passwort angegeben, so erscheint
die Loginmaskeerneut, mit einer Fehlermeldung.
Sind die Eingaben korrekt, aber der Nutzer besitzt nicht die notwendige Berechtigung, so
erscheint die Loginmaskemit einem Hinweis, dass die benötigte Berechtigung nicht vorliegt.
Ist der Nutzer das erste Mal in der TimeFlipPlattform eingeloggt, so muss er einen
Disclaimertextbestätigen.

1.6.1. Logfiles
Alle wichtigen Ereignisse, die das System insgesamt betreffen, sollen in zwei unterschiedlichen Log-Dateien direkt am
Webserver gespeichert werden. Anhand der Log Dateien soll sowohl das fehlerfreie Zusammenspiel der
Systemkomponenten nachvollziehbar sein, als auch Fehlerbehebung anhand von Warnungen, und Errors aus dem laufenden
Betrieb ermöglicht werden.
Dabei soll eine der Log-Dateien alle Informationen loggen, die andere nur die Warnungen und Fehlermeldungen. Zu
Ereignissen zählen zum Beispiel das Hinzufügen neuer Verbindungen oder Geräte oder Ausfälle der Sensorstationen,
Raspberry PIs oder des Webservers. Ebenso soll eine Log-Datei auf jedem Raspberry Pi geschrieben werden. Bitte loggen Sie
hier die Kommunikation mit den Sensorstationen, Übertragungen an den Webserver, Datenlöschungen, erfolgreiche
Verbindungsversuche und Verbindungsprobleme bzw. -ausfälle sowohl mit Sensorstationen als auch
dem Webserver.

Wie dokumentiere ich gefunden Fehler?
• Klassische Fehlermeldung eines Endnutzers
– „Die Anwendung funktioniert nicht“
– „Das Anwendung stürzt immer ab“
– „Immer wenn ich eine Zeitbuchung eingebe, kommt ein Fehlerdialog“
• => Fehlermeldungen sollten den Fehler reproduzierbar(!)beschreiben:
z.B.
1. Wann trat der Fehler auf? (=> Analyse des Logfiles)
2. Wer hat den Fehler gefunden? (=> ggf. für Rückfragen beim Nutzer)
3. In welcher Funktion trat der Fehler auf (=> genauere Lokalisation des
möglichen Fehlers)
4. Mit welchen Eingabedaten kann der Fehler ggf. reproduziert werden? (=>
Nachvollziehbarkeit für Entwickler)
5. Ein Screenshot hilft oft ungemein! (Achtung ggf. Datenschutz!)
• Fehler können übrigens auch an mangelnder Nutzerdokumentation /
Nutzerschulung / schlechtem UI-Design liegen.

Zielsetzung und Ergebnis des Abnahmetests
• Typischerweise letzter Schritt vor der Inbetriebnahme
• Gewährleistung der Produktionsreife
• Testdurchführung durch den Auftraggeber(!)
– Allerdings kann der Auftraggeber ggf. auf die Testfälle der Integrationstests zurückgreifen (bzw.
der Auftragnehmer im Integrationstest auf Testfälle aus Abnahmetest)
• Typische Ausgänge eines Abnahmetests
o Abnahme: Produkt ist abgenommen
o Bedingte Abnahme: Produkt wird abgenommen, aber es müssen
noch eine festgelegte Liste von Mängeln behoben werden.
o Ablehnung: Abnahme wird nicht erteilt, eine Liste Mängel müssen
behoben und zur erneuten Abnahme vorgelegt werden.

Durchführung des Abnahmetests
• Ausgangsbasis: Testdrehbuch für die Abnahme (ggf. abgeleitet
aus Testdrehbuch für System-/Integrationstests)
• Durchführung der Tests

– früher: offiziell unterschriebenes Dokument
